# Jev (TypeSafe AI "System One" typed-judgment model) — Usage Catalog: High-Energy & Nuclear Physics

**Scope.** Jev is a non-generative, typed-judgment model: JSON state in → structured judgments out (Choice / Noul / Score, with probabilities + confidence), many questions per call, sub-100 ms latency (roadmap sub-10 ms), ~$0.04/Mtoken, 32K context. It is best understood as a cheap, fast, *semantic gut-check layer* that complements — never replaces — the deterministic, hardware-grade classifiers already deployed in HEP. This catalog lists 14 grounded usages, each with current practice & bottleneck, concrete primitive design, latency/cost rationale, evidence citations, and a confidence grade.

**Timescale discipline (critical).** At the LHC, the Level-1 hardware trigger decides within microseconds on FPGAs: ATLAS L1 "≤ 2.5 µs", CMS L1T "a 99.75% reduction within 3.8 microseconds" [^1^][^2^]; even ML-in-L1 (AXOL1TL) requires "a latency of only 50 ns" [^3^]. **L1 is NOT a fit for Jev.** The software High-Level Trigger runs on CPU/GPU farms with "an average of a few hundred milliseconds" per event (CMS Run 2 measured mean 451 ms) [^4^][^5^] and LHCb buffers events for minutes in a 30 PB disk buffer between HLT1 and HLT2 [^6^] — **HLT-adjacent and post-HLT tasks are a possible fit**. Offline DQM, certification, calibration review, logbook, and analysis-support tasks operate at seconds-to-days — **clear fits**.

## Usage 1 — HLT semantic advisory layer (post-reconstruction, pre-commit judgments)
**One-liner:** Cheap parallel gut-checks over HLT-reconstructed event summaries (or stream/parking decisions), composed in code with the deterministic HLT filters — e.g., "does this parked/scouting event deserve promotion to the prompt stream?" or "is this trigger-path's decision consistent with the event features?"
**Current practice & bottleneck:** HLT menus evaluate hundreds-to-thousands of hard-coded selection lines: CMS runs "𝒪(1200) instances stemming from 𝒪(200) algorithms" at ~451 ms/event [^5^]; LHCb evaluates "1000s of different physics selection lines" in HLT2 [^7^]. Decisions are brittle threshold cuts on reconstructed quantities; borderline events are either prescaled away or parked, and menu tuning is a slow expert loop.
**Primitive design:** State = JSON of HLT-level object four-vectors, path decisions, rate/lumi context. Per event or per ~kHz-subsampled batch: Noul("kinematically consistent with a [displaced-vertex / soft-lepton / dijet] signature?"), Choice(promote to {prompt, parking, scouting, discard}), Score(0–4 interest rubric). Verdicts act as *advisory tags* or prescale modifiers — the hard accept/reject stays deterministic.
**Why latency/cost matters:** HLT budget is ~100 ms–1 s/event; sub-100 ms Jev calls fit only as a *parallel* side-channel or on buffered/parked data (LHCb's multi-minute HLT2 buffer gives minutes of slack [^6^]). At 100 kHz input, full-rate semantic inference is impossible for any transformer-class model; Jev's parallelism lets it sample/triage at kHz-class rates where an LLM-based judge would be unaffordable.
**Evidence:** [^5^][^6^][^7^][^8^] | **Confidence: Medium** (fit is in buffered/scouting/parking paths, not the synchronous HLT chain).

## Usage 2 — Anomaly-trigger output triage (semantic labeling of AXOL1TL/CICADA streams)
**One-liner:** Classify and prioritize events captured by the new L1 anomaly-detection triggers — Noul/Choice over object-level features: "is this plausibly detector noise vs. a coherent physics topology?"
**Current practice & bottleneck:** CMS deployed AXOL1TL and CICADA in Run 3; they select "anomalous events … primarily contributing to scouting data streams" at ~1 kHz parking rate, orthogonal to standard triggers [^9^][^10^][^11^]. The downstream problem is exactly a *triage* problem: thousands of Hz of unlabeled anomalous events that analysts must sift, with no ground truth. CMS is already exploring "a second anomaly-detection layer … for the software-based High-Level Trigger, aiming to improve the purity of the anomaly stream" [^12^].
**Primitive design:** State = L1/HLT object lists (pT, η, φ of MET, e/γ, μ, jets — precisely the AXOL1TL input signature [^13^]) + anomaly score. Questions: Choice(anomaly type: {noise/instrumental, known-SM-rare, BSM-candidate-topology}), Score(topology coherence 0–4), Noul per hypothesized topology. Compose in code to rank events for analyst attention and to build "look-elsewhere" control samples.
**Why latency/cost matters:** Runs offline-ish on recorded scouting data or in the HLT buffer; needs to be cheap enough to cover ~1 kHz streams and thousands of parallel topology questions per event — precisely the many-questions-per-call regime.
**Evidence:** [^9^][^10^][^11^][^12^][^13^] | **Confidence: High** (literature explicitly names the second-layer triage need).

## Usage 3 — DQM shifter verdict support (lumisection/histogram gut-checks)
**One-liner:** Parallel Noul/Score verdicts over DQM histogram summaries per lumisection (~23 s of data), replicating the shifter's "good / bad / suspicious" eyeball judgment.
**Current practice & bottleneck:** "DQM is currently performed by human shifters, which is costly and results in limited accuracy"; "Shifter rotation leads to variations in judgements" [^14^][^15^]. CMS certifies data "on a run by run basis" by "human based inspection of histograms", with ML now targeting "LS-by-LS granularity of the decisions" [^16^]. Autoencoder anomaly detection exists (ECAL, HCAL, tracker, JetMET [^17^][^18^]) but outputs bare anomaly scores; the *semantic* verdict ("which subsystem, what failure mode, does this LS certify?") remains human. LHCb prototyped RLHF human-in-the-loop DQM for exactly this gap [^14^].
**Primitive design:** State = per-LS histogram statistics (means, RMS, KS-vs-reference, occupancy maps vectorized), DCS flags, previous verdicts. Questions per LS × subsystem: Noul("data-taking quality nominal?"), Choice(failure mode: {gain drift, dead channel, noise burst, beam background, none}), Score(certification 0–4: good→bad). Compose majority/confidence-weighted verdicts; route only low-confidence LSs to humans — the "checker" role of the RLHF prototype [^14^].
**Why latency/cost matters:** LS cadence is 23 s; hundreds of subsystems × dozens of questions must complete each LS — trivially within Jev latency, and at $0.04/Mtoken the per-fill cost is negligible vs. shifter FTE cost.
**Evidence:** [^14^][^15^][^16^][^17^][^18^] | **Confidence: High** (directly matches deployed DQM-ML literature and its stated gaps).

## Usage 4 — Run classification & defect-entry assistance (good-run-list pipeline)
**One-liner:** Semantic classification of runs and luminosity blocks into the experiment's defect taxonomy, pre-filling the defect database that experts sign off.
**Current practice & bottleneck:** ATLAS records "a deviation from a nominal detector condition" as *defects* per luminosity block, combined into virtual defects and good-run lists; the system is "filled both by people and software", with 619 defects + 172 virtual defects already in 2011 [^19^]. Human shifter/expert signoff gates every run ("The administrative interface will not permit the generation of official good run lists … if any UNCHECKED defects are present" [^19^]). CMS certification similarly certifies run-by-run by hand [^16^].
**Primitive design:** State = run metadata (rates, HV/DCS alarms, DQM anomaly counts, shifter comments). Questions: Choice(defect taxonomy node), Noul("LB usable for physics class X?"), Score(severity 0–4). Output = proposed primary-defect entries + confidence; low-confidence entries escalate to experts.
**Why latency/cost matters:** Runs complete on minutes-to-hours timescales; cost-per-run is trivial. The value is consistency across thousands of runs and reducing expert review load.
**Evidence:** [^19^][^16^] | **Confidence: High** (mirrors an existing, documented human workflow).

## Usage 5 — LHC beam-loss event triage (post-mortem classification of dumps)
**One-liner:** Classify each beam-abort/loss event by type and severity from BLM-pattern summaries — OK / NOT-OK / Warning, UFO vs. asynchronous dump vs. other — the exact task CERN already automated.
**Current practice & bottleneck:** "Machine protection experts use these measurements to label anomalies that occur around the moment of beam extraction. However, this requires expert knowledge and time" [^20^]. CERN deployed "an automated beam loss analysis tool … in operation since November 2023" that "not only classifies events into NOT-OK and OK, but also indicates the BLM location of the anomaly" [^21^]; deep-learning variants classify "asynchronous beam dump tests and Unidentified Falling Objects — with an accuracy above 98%" [^20^]. The operational loop still needs expert confirmation and judgment about *marginal* cases and about adapting thresholds ("thresholds need to be adapted in case of modified loss patterns" [^21^]).
**Primitive design:** State = BLM time-series summary (peak locations, octant aggregates, thresholds crossed, machine mode, beam energy). Questions: Choice(event type {OK, UFO, ASD, other}), Score(severity 0–4), Noul("pattern consistent with historical class X?"), plus Noul("are current thresholds still calibrated given recent fills?").
**Why latency/cost matters:** Post-mortem runs seconds after a dump; thousands of data sources per event make per-question parallelism valuable; negligible cost vs. machine-protection stakes.
**Evidence:** [^20^][^21^] | **Confidence: High** (deployed-system precedent; Jev fits as the semantic/advisory layer around the deterministic classifier).

## Usage 6 — Online calibration & alignment decision support
**One-liner:** Gut-check verdicts on freshly computed calibration/alignment constants before they are committed to the trigger/reconstruction chain.
**Current practice & bottleneck:** LHCb's Run-3 model depends on "real-time calibration, high-level monitoring" with "the alignment framework [calculating] updated alignment constants at regular intervals, i.e., per fill or run, as soon as sufficient data has been collected" [^6^][^22^]. "The online LHCb calibration ensures offline-quality reconstruction, enabling trigger selection with high signal efficiencies" [^22^] — so a bad constants commit is physics-damaging. Sanity-checking new constants (residual pulls, χ², comparisons to previous fill) is an expert checklist task.
**Primitive design:** State = old vs. new constants, residual/χ² summaries, fill conditions. Questions: Noul("new constants consistent with expected drift?"), Score(commit readiness 0–4), Choice({commit, commit-with-warning, hold for expert}). Parallelize over subdetectors (VELO, UT/SciFi, muon, RICH mirrors, ECAL — the exact decomposition LHCb uses [^22^]).
**Why latency/cost matters:** Per-fill cadence (hours) with a human in the loop; cost irrelevant, latency trivially adequate. Value = uniform application of the checklist across hundreds of constant sets.
**Evidence:** [^6^][^22^] | **Confidence: Medium-High** (practice is documented; the advisory layer is a design proposal, not deployed ML).

## Usage 7 — Simulation-vs-data (MC validation) verdicts
**One-liner:** Automated semantic judgment on data/MC comparison plots — "is this distribution agreement acceptable for production release?" — extending today's histogram-comparison tools with typed verdicts.
**Current practice & bottleneck:** ATLAS's JEM "has already become a standard to validate ATLAS simulation … by automatically comparing and classifying certified reference histograms with the new ones", presenting "an easy color code … where only the most important ones are displayed" for shifters [^23^]. CMS runs "a validation tool within the CMS DQM framework" to "check the agreement of reconstructed track properties between Data and Monte-Carlo … [and] provide prompt feedback" [^24^]. The statistical comparison is automated; the *judgment call* ("acceptable / needs expert") is still manual, across thousands of histograms per campaign.
**Primitive design:** State = per-distribution comparison metrics (χ²/ndf, KS, shape features) + campaign context. Questions: Score(agreement 0–4), Choice(failure class {normalization, shape, tails, none}), Noul("release-blocking discrepancy?"). Compose to triage only red-flag plots to MC contacts.
**Why latency/cost matters:** Validation campaigns produce O(10⁴) histograms per release; per-question parallelism + negligible cost is the whole game.
**Evidence:** [^23^][^24^] | **Confidence: High**.

## Usage 8 — Analysis-level systematic-uncertainty sanity checks
**One-liner:** A battery of atomic Noul checks over an analysis's systematic configuration — closure tests, nuisance-parameter pulls, unit/consistency checks on inputs — run in parallel every time the analysis is re-executed.
**Current practice & bottleneck:** Analyses rely on manual checklists for validation regions, closure tests, and pull inspection; infrastructure exists to make such checks *data-addressable*: the ATLAS defect system notes "It is also possible to ignore specific primary defects during the virtual defect computation, again to facilitate studies of systematic uncertainties" [^19^], and inter-experiment MC-agreement campaigns show the appetite for standardized verdicts ("Validation of each experiment's ability to reproduce identical samples is shown" [^25^]). LLM-agent HEP pipelines are emerging to automate analysis steps but "the final outputs still show stochastic variation", motivating independent verification layers [^26^].
**Primitive design:** State = fit results (pulls, correlations), closure-test residuals, cut-flow tables, config diffs. Questions: Noul per atomic check ("pulls within ±1?", "ABCD closure within tolerance?", "systematic X correctly decorrelated across eras?"), Score(overall readiness rubric). Deterministic code aggregates verdicts into a gate.
**Why latency/cost matters:** Checks must run on *every* iteration of an analysis (many times/day, for years, across thousands of analyzers) — cheap typed judgments beat both human time and LLM-judge cost/latency.
**Evidence:** [^19^][^25^][^26^] | **Confidence: Medium** (components are established practice; packaged semantic check-lists are a proposal).

## Usage 9 — Event classification & selection support (pre-BDT triage and cut-flow audits)
**One-liner:** Not a replacement for the BDT — a semantic layer that audits selection logic and triages which candidate events/samples merit full multivariate treatment.
**Current practice & bottleneck:** "Multivariate machine learning techniques … have become standard tools in most HEP analyses" via TMVA/ROOT [^27^]; BDTs "have been a popular algorithm for classification … contributing even to the Higgs discovery in 2012" [^28^]. BDT inference itself is microsecond-cheap, so Jev adds nothing at inference. The bottlenecks are *upstream*: choosing which variables/cuts/regions to use, spotting pathological cut-flows, labeling training data, and explaining why events flip categories across selection versions — all manual expert judgment.
**Primitive design:** State = cut-flow table, per-cut efficiency/purity numbers, variable list + correlations. Questions: Noul("cut C3 likely dominated by unmodeled background?"), Choice(which validation region to add), Score(selection robustness rubric). For small-RoI samples (rare processes): parallel per-event Noul("consistent with signal hypothesis H_i?") as a *cross-check* on the BDT's decision boundary.
**Why latency/cost matters:** Runs at analysis-iteration cadence (offline, seconds-minutes); cheap enough to interrogate every cut and every boundary event, which a human or LLM reviewer never will.
**Evidence:** [^27^][^28^] | **Confidence: Medium** (strong grounding in practice; the Jev-shaped niche is audit/triage, not classification).

## Usage 10 — Particle-ID advisory for ambiguous tracks and calibration samples
**One-liner:** Typed judgments over combined PID likelihoods (CombDLL/ProbNN-style features) for tracks where classifiers disagree with each other or with kinematic expectations — routing ambiguous cases for reprocessing or systematic flagging.
**Current practice & bottleneck:** LHCb's global PID feeds subdetector likelihoods "as input into an artificial neural network … provid[ing] a single probability (typically called ProbNNX) for each particle hypothesis" [^29^]; multiclass DNN/XGBoost/CatBoost successors reach "ROC AUCs ≈ 0.91–0.99" but suffer "efficiency degradation in case the testing scenario is significantly different from training" [^30^] — i.e., the open problem is knowing *when not to trust* the PID model, especially across data-taking periods (models are re-tuned per era [^29^]).
**Primitive design:** State = per-track DLL vector, ProbNN probabilities, kinematics, event multiplicity, era. Questions: Noul("PID assignment trustworthy for this track?"), Choice(species tie-break when two ProbNNs within margin), Score(domain-shift risk of this subsample 0–4). Compose flags per calibration sample to detect mis-tuned eras.
**Why latency/cost matters:** Offline, per-track at 10⁶–10⁹ track scale → only a very cheap model can sit in this loop; Jev's cost profile is the enabling factor, deterministic NNs remain the primary classifier.
**Evidence:** [^29^][^30^] | **Confidence: Medium-Low** (domain-shift problem is documented; advisory-layer design is extrapolation).

## Usage 11 — Neutrino-event reconstruction & selection triage (LArTPC)
**One-liner:** Semantic triage over CNN-reconstructed neutrino events: does the reconstruction verdict make sense; which rare-signal candidates (supernova burst frames, beam neutrinos) deserve retention/alerting?
**Current practice & bottleneck:** CNNs are the established LArTPC workhorse: MicroBooNE demonstrated neutrino-vs-cosmic classification ("87.1±0.5% efficiency with 72.9% purity" single-plane [^31^]) and sparse semantic segmentation at "≈0.5 s" inference per event [^32^]. DUNE's trigger challenge is extreme: "~40 terabits per second", needing "O(10⁴) overall background suppression" for supernova-burst candidates, with CNN-based frame classification plus a "higher-level data selection decision" over "frames across the entire the detector over a 10 second period" [^33^]. That higher-level, detector-wide coincidence/context judgment is exactly a semantic-choice task.
**Primitive design:** State = per-frame CNN scores + reconstruction summaries + multi-frame coincidence features. Questions: Choice(frame class {beam ν, SN burst candidate, cosmogenic, instrumental}), Noul("reconstruction self-consistent across three wire planes?"), Score(alert priority 0–4 for SNEWS-style early warning [^34^]).
**Why latency/cost matters:** DUNE's supernova window is seconds — ample for sub-100 ms judgments; the 40 Tb/s raw stream is decimated by deterministic CNNs first, and only the trickle of candidates needs the semantic layer, so cost stays negligible.
**Evidence:** [^31^][^32^][^33^][^34^] | **Confidence: Medium-High**.

## Usage 12 — Dark-matter / low-background cut advisory
**One-liner:** Advisory verdicts on borderline events near analysis cuts and on data-quality conditions in rare-event searches — where every accepted background event and every misapplied cut is analysis-critical.
**Current practice & bottleneck:** ML cuts are established: LZ built "three test statistics used as input features in a boosted decision tree, which classifies events as signal or background", improving projected 40 GeV WIMP sensitivity "by 8%" [^35^]; DEAP-3600 uses XGBoost BDTs for neck-alpha discrimination [^36^]. But cuts sit on *blinded* data with extreme background-rejection requirements (single-electron backgrounds "can cause a steeply rising background at low thresholds" [^37^]), and "development of data quality monitoring tools … are essential to achieve a robust science result for an extremely rare signal" [^35^]. Borderline-event disposition and DQ verdicts remain expert-judgment bottlenecks.
**Primitive design:** State = per-event S1/S2 features, BDT score, DQ context, (blinded) region flags. Questions: Score(event pathology 0–4), Noul("consistent with known accidental-coincidence pathology?"), Choice({accept-advisory, veto-advisory, expert-review}). Advisory only — physics cuts remain frozen and deterministic to preserve blindness.
**Why latency/cost matters:** Fully offline, tiny event counts; the binding constraint is *consistency* of expert judgment across years of runtime, which cheap uniform typed judgments provide.
**Evidence:** [^35^][^36^][^37^] | **Confidence: Medium**.

## Usage 13 — Shift assistance & electronic-logbook triage
**One-liner:** Real-time typed classification of logbook entries and control-room alerts — auto-categorization, severity scoring, routing to the on-call expert — plus shift-summary consistency checks.
**Current practice & bottleneck:** Fermilab's ADEL logbook "has recorded nearly one million user-generated entries"; prior ML attempts (OCR of screenshots, image categorization) had "moderate success" but stalled for "lack of resources and time", and current work builds "a semantic search prototype capable of searching ADEL quickly" [^38^]. Control-room operators "need to analyse thousands of data sources" during anomaly response [^20^].
**Primitive design:** State = log entry text + metadata (system, time, machine state) / alarm stream slice. Questions: Choice(category & subsystem), Score(urgency 0–4), Noul("duplicate of known issue K?"), Noul("does shift summary match logged events?"). Parallel over the incoming stream.
**Why latency/cost matters:** Entries arrive continuously for years; only sub-cent costs and sub-second latency make always-on classification viable — precisely Jev's envelope, not an LLM's.
**Evidence:** [^38^][^20^] | **Confidence: High**.

## Usage 14 — Paper & documentation cross-checks (units, internal consistency, boilerplate compliance)
**One-liner:** Parallel Noul batteries over manuscripts/notes/TDRs: unit consistency of every quoted number, table-vs-text agreement, reference/figure consistency — a fast deterministic-grade lint layer for physics prose.
**Current practice & bottleneck:** HEP collaborations run multi-stage internal review of hundreds of papers/year; checking numerical/unit consistency is manual and error-prone. LLM agents are being piloted for HEP analysis automation with explicit concerns about reliability ("models do not produce fully deterministic results" [^26^]), and domain LLMs (FeynTune, Astro-HEP-BERT) are being built for HEP text [^39^] — but generative LLMs are slow/costly as *verifiers* at scale. A typed, non-generative verifier is the natural complement: LLM drafts/finds, Jev judges.
**Primitive design:** State = extracted (quantity, value, unit, context) tuples + paired claims from text/tables/figures. Questions: Noul("units dimensionally consistent?"), Noul("table value equals text value within stated uncertainty?"), Score(claim-support 0–4 vs. cited figure). Hundreds of questions per paper in one/few calls.
**Why latency/cost matters:** Review cycles repeat per draft; sub-100 ms × thousands of checks × hundreds of papers needs exactly this cost/latency class to run as CI on every commit.
**Evidence:** [^26^][^39^] | **Confidence: Medium** (practice and tooling trends are documented; the specific lint-layer packaging is a proposal).

## Cross-cutting fit assessment
| Layer | Timescale | Jev fit |
|---|---|---|
| L1 hardware trigger (FPGA NN: AXOL1TL 50 ns, L1T 3.8–4 µs) | ns–µs | **No** — physics of the stack forbids it [^2^][^3^] |
| HLT synchronous path (CPU/GPU farm) | ~100–500 ms/event | **Marginal** — parallel side-channel only [^4^][^5^] |
| Buffered HLT / parking / scouting (LHCb 30 PB buffer; 1 kHz AD streams) | seconds–minutes | **Yes** [^6^][^10^] |
| Online DQM/calibration/beam post-mortem | 10 s–hours | **Clear fit** [^14^][^21^][^22^] |
| Offline certification, analysis support, logbook, paper checks | minutes–days | **Clear fit** [^19^][^38^] |
